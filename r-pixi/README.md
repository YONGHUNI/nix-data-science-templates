# R + Pixi

Nix provides `pixi` inside the development shell; Pixi manages the project-local R runtime, R packages available through conda-forge, native dependencies, and `pixi.lock`.

This template mirrors the repository's `python-pixi` workflow so R and Python projects can use the same environment-management model.

## What is pinned

The initial manifest pins R to:

```text
R 4.5.3
```

`pixi.lock`, generated by the first `pixi install`, records the exact resolved package builds and transitive native dependencies. Commit the lockfile.

The starter environment contains:

```text
R 4.5.3
IRkernel
data.table
dplyr
ggplot2
compilers
make
pkg-config
```

The compiler toolchain is included so common CRAN source packages can be built inside the Pixi environment when a binary package is unavailable or when a newer source release is required. On Linux this is conceptually similar to keeping Rtools available on Windows, but the compiler suite and build tools are resolved as project dependencies rather than installed globally.

## Enter the Nix development shell

```bash
nix develop
```

Nix supplies the Pixi executable from the pinned `nixpkgs` input.

On NixOS, conda-forge binaries require the generic Linux dynamic loader compatibility provided by:

```nix
programs.nix-ld.enable = true;
```

This is a host-level setting and intentionally does not belong in the project template.

## Install the project environment

```bash
pixi install
```

Pixi creates the runtime environment under `.pixi/` and generates `pixi.lock`.

Verify it with:

```bash
pixi run R --version
pixi run R --vanilla -q -e 'cat(R.version.string, "\n"); library(data.table); library(dplyr); library(ggplot2)'
```

For batch work:

```bash
pixi run Rscript analysis.R
```

For an interactive R process:

```bash
pixi run R
```

## Add R packages

Conda-forge R package names normally use the `r-` prefix:

```bash
pixi add r-tidyr r-readr
```

For geospatial work:

```bash
pixi add r-sf r-terra
```

Prefer `pixi add` over `install.packages()` for dependencies that should be reproducible. A package installed manually from inside R is not represented by `pixi.toml` / `pixi.lock`.

## Building CRAN packages from source

The base template includes the conda-forge `compilers` metapackage plus `make` and `pkg-config`. This provides the standard C, C++, and Fortran compiler toolchain needed by many R source packages.

For example:

```r
install.packages("somepackage", type = "source")
```

can build against the compiler suite available inside the Pixi environment.

The compiler suite does not automatically provide every external library a package may need. Add project-specific native dependencies through Pixi as required. For GIS packages, for example:

```bash
pixi add gdal geos proj
```

Other projects may require libraries such as NetCDF, HDF5, OpenSSL, libcurl, or XML libraries. Keep those dependencies in `pixi.toml` rather than relying on accidental host-system availability.

A package installed directly with `install.packages()` is not captured by `pixi.lock`. Use direct source installation for exceptional or temporary cases; if long-term reproducibility matters, record and pin the source explicitly in the project workflow.

## Why `renv` is not included

For conda-forge-packaged dependencies, Pixi already manages:

- the R interpreter version
- R package versions
- native libraries used by R packages
- dependency solving
- the project lockfile

Adding `renv` by default would create two overlapping package managers.

Keep the existing `r-renv` template for projects that are specifically CRAN/renv-oriented, rely heavily on R packages that are not practical to obtain through conda-forge, or need compatibility with an established renv workflow.

## Positron

Positron has experimental discovery support for Pixi-managed R installations.

In Positron Settings, enable:

```text
positron.r.interpreters.pixiDiscovery
```

After `pixi install`, select the R interpreter associated with the current Pixi project.

The project-local executable lives under `.pixi/`; do not hard-code its internal resolved path into the repository.

`r-irkernel` is included so the environment can also be used for R Jupyter notebooks.

## Laptop and server workflow

The template currently targets:

```text
linux-64
```

That allows the same `pixi.toml` and committed `pixi.lock` to be used on x86_64 Linux laptops/workstations and x86_64 Linux servers.

On each machine:

```bash
nix develop
pixi install
```

The `.pixi/` directory is machine-local and must not be committed.

For a remote/headless server, normal batch execution is:

```bash
pixi run Rscript analysis.R
```

When using Positron against a remote workspace, resolve the Pixi environment on the remote host and use the remote Pixi-managed R interpreter.

The base template deliberately contains no GPU-specific R dependencies. This keeps the same project environment usable on both a laptop without CUDA and a GPU server. If an R project later needs CUDA-specific packages, add them as a dedicated Pixi feature/environment rather than making the portable base environment GPU-dependent.

## Project layout

```text
my-project/
├── flake.nix
├── flake.lock
├── pixi.toml
├── pixi.lock        # generated by Pixi; commit this
├── .gitignore
├── .pixi/           # generated runtime environment; do not commit
└── R source files
```

The responsibilities are intentionally separated:

```text
Nix / flake.nix
├── Pixi executable
└── outer development shell

Pixi / pixi.toml + pixi.lock
├── R runtime
├── R packages
├── compiler/build toolchain
├── native dependencies
└── reproducible dependency resolution
```

## Rocker

For interactive research and batch analysis on similarly configured NixOS/Linux machines, this template can remove much of the need for a Rocker container: the R runtime, R packages, build toolchain, and their native dependencies are already project-local and locked by Pixi.

Rocker still has a distinct role when a project needs a Docker/OCI image boundary, deployment as a container, isolation from the host OS, CI based on container images, or easy handoff to collaborators whose environment is Docker rather than Nix/Pixi.

In other words, `r-pixi` can be the default research environment without claiming to replace containerization itself.

## Reproducibility

Commit:

- `flake.nix`
- `flake.lock`
- `pixi.toml`
- `pixi.lock`

Do not commit `.pixi/`.

`flake.lock` pins the Nix side, including the Pixi executable. `pixi.lock` pins the R runtime, R packages, compiler/build toolchain, and resolved conda-forge native dependencies.

# Python + Pixi — Sapelo2 fast-storage preset

The purpose of this preset is **storage I/O performance**, not rootless Nix itself. Compared with `python-pixi`, its `flake.nix` shell hook places Pixi's download/cache data and detached environments on Sapelo2's fast `/lscratch` storage:

| Setting | Location |
|---|---|
| `PIXI_CACHE_DIR` | `/lscratch/$USER/pixi-cache` |
| `detached-environments` | `/lscratch/$USER/pixi-envs` |
| Generated project configuration | `.pixi/config.toml` |

The hook creates these directories and writes the detached-environment setting whenever `nix develop` is entered. This reduces package download/extraction and environment I/O on slower home/project storage. Nix provides Pixi, while Pixi handles Python dependencies and `pixi.lock`. The fast-storage paths must be available and writable; consult cluster scratch retention policies.

## Enter the development shell

```bash
nix develop
```

The shell provides Pixi from the pinned Nix environment. No separate Pixi installation is required.

On NixOS, Conda-style binaries may require `programs.nix-ld.enable = true;` at the host level. This is a host configuration concern rather than a project dependency.

## Create/install the environment

The project already contains `pixi.toml`. Run:

```bash
pixi install
```

Pixi resolves the manifest, stores installed environments in the configured detached location `/lscratch/$USER/pixi-envs`, and generates/updates `pixi.lock`. The `.pixi/` directory stores generated local configuration rather than the main runtime environment.

The initial manifest includes:

```text
Python 3.12
ipykernel
NumPy
pandas
SciPy
matplotlib
```

## Work inside the environment

Open an interactive shell with:

```bash
pixi shell
```

Or run commands without activating a shell:

```bash
pixi run python --version
pixi run python analysis.py
```

For scripts, batch jobs, and reproducible commands, `pixi run` is generally preferable to relying on shell activation.

## Add dependencies

Add packages through Pixi so the manifest and lockfile remain synchronized:

```bash
pixi add xarray dask netcdf4
```

For geospatial work, for example:

```bash
pixi add gdal rasterio geopandas pyproj shapely
```

Pixi updates `pixi.toml` and resolves the corresponding `pixi.lock`.

## Project layout

```text
my-project/
├── flake.nix
├── flake.lock
├── pixi.toml
├── pixi.lock        # generated by Pixi; commit this
├── .gitignore
└── .pixi/config.toml # generated fast-storage configuration; do not commit
└── source files
```

The responsibilities are intentionally separated:

```text
Nix / flake.nix
├── Pixi executable
├── outer development shell
└── host/system-level tooling

Pixi / pixi.toml + pixi.lock
├── Cache: /lscratch/$USER/pixi-cache
├── Detached environments: /lscratch/$USER/pixi-envs
├── Python
├── Python packages
├── Python-coupled native libraries
├── project environments
└── reproducible dependency resolution
```

## Single vs multiple environments

For a simple project, the default Pixi environment is enough.

Pixi also supports project-level features and multiple environments. That makes this template a better fit than the `python-conda`/`nimba` template when one repository intentionally needs several related environments, for example separate weather-model stacks with incompatible Python, JAX, PyTorch, or CUDA user-space dependencies.

Keep the `python-conda` template simple: it is designed around one canonical project-local `.conda` environment. Use this Pixi template when the project itself needs richer environment composition.

## Optional editor and notebook integration

After `pixi install`, point your preferred editor or Jupyter client to the Python interpreter in the project-local `.pixi/` environment. No editor integration is required for CLI use. `ipykernel` is included for standard Jupyter-compatible notebooks.

## Reproducibility

Commit:

- `flake.nix`
- `flake.lock`
- `pixi.toml`
- `pixi.lock`

Do not commit `.pixi/` or generated cache/environment files on `/lscratch`.

`flake.lock` pins the Nix side, including the Pixi executable. `pixi.lock` pins Pixi's resolved project dependencies. This gives the Pixi template stronger package-level reproducibility by default than an unlocked `environment.yml` workflow.
